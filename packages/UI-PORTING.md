# Aboard UI 移植规范

本文规范如何将第三方 React UI 组件移植到 `@abworks-dev/ui` 和 `@abworks-dev/ai-ui`，是仓库对源码来源、Base UI 适配、Aboard 样式、权威边界和验证的约定。

## 1. 源码与来源追溯

- 每份上游源码都固定到不可变的 commit 或 release。在包的来源记录中保存 URL、commit、许可证和源码路径。
- 上游许可证允许时，优先复制源码（source-copy-first）：先保留上游组件结构、状态机、复合导出、键盘行为和已文档化的 props，再适配基础设施。
- 禁止在运行时导入第三方应用代码。将所需源码移植到负责该能力的包，并记录适配。
- 上游基线与 Aboard 适配必须分开。视觉或原语修改都应作为明确差异记录，不能无记录地重写。
- 对大量派生自上游的文件，保留许可证和署名头。

## 2. 修改前检查与依赖归属

编辑组件前：

1. 阅读路径最近的 `AGENTS.md`、本文和包的来源记录。
2. 明确上游原语依赖，以及每项依赖在 Aboard 中的准确归属。
3. 核对 `@abworks-dev/ui` 和 `@base-ui/react` 的公开导出与已安装类型定义；禁止猜测 Base UI 的 prop、part、事件、CSS 变量或 data attribute。
4. 所需原语缺失时，先在 `@abworks-dev/ui` 修复或明确该缺口范围。禁止在 `@abworks-dev/ai-ui` 创建私有原语或简化替代方案。
5. 修改行为前，先取得类型检查、聚焦测试的基线；交互组件还要准备浏览器 smoke 路由。

## 3. 适配策略

按以下顺序选择：

- **成对基线（Golden pair）**：存在等价的 Radix 与 Base UI 源码时，对比固定版本的成对源码，并将 Aboard 定制重新应用到 Base UI 源码。大型组件优先三方合并，而非重新手写。
- **参考映射（Reference mapping）**：不存在成对源码时，依据 `packages/ui/BASE-UI-MAPPING.md` 中已验证的映射和当前包类型定义，每次适配一个原语家族。
- **本地实现（Local implementation）**：只有上游和 Base UI 都不提供所需行为时，才使用原生 HTML 或本地实现。说明原因，并明确测试缺失的行为。

禁止盲目全局替换。每个 prop 或状态属性都必须针对具体 Base UI 组件和版本核实。

## 4. Base UI 与 Aboard 样式规则

- 只有目标 part 支持时，才能把 Radix `asChild` 改为 Base UI `render` 组合；否则使用显式元素，并转发其支持的 props。
- 从目标原语实际 DOM 契约映射展开/关闭、选中、高亮、禁用和方向状态。不得假设 `data-state` 总能映射为 `data-open`。
- 保留语义化 HTML、可访问名称、键盘导航、焦点返回、键入查找、Escape 处理和外部点击行为。
- 在兼容的前提下保留上游 class 结构和变体意图。使用 Aboard 语义 Token 与逻辑属性替换原始颜色、字体、圆角、阴影和对方向敏感的硬编码偏移。
- AI UI 没有独立的主题权威。组件消费 `@abworks-dev/ui` Token，并保持与浅色/深色、RTL、窄屏布局及包的视觉主题作用域兼容。
- 除非记录了有意的破坏性变更，否则保留复合组件名称和公开导出。

## 5. 权威与副作用

展示组件可以管理本地交互状态：展开/关闭、焦点、滚动、定时器、媒体元素状态和动画生命周期。

组件禁止拥有模型调用、传输、持久化、凭据、文件系统访问、插件执行、工具执行或权限审批。这些能力仍归调用方所有，通过类型化 props 和回调表达。剪贴板、下载、上传和播放操作必须是用户明确触发的回调，或有清楚说明的浏览器本地行为。

## 6. 完整性模型

编译通过或看起来相似，都不代表移植完成。独立跟踪四个维度：

- **接口（Surface）**：导出、props、插槽、复合 part 和已文档化的变体。
- **行为（Behavior）**：状态转换、流式时序、键盘/焦点行为、回调、错误和加载状态。
- **视觉（Visual）**：语义 Token、响应式布局、动画、深色模式、RTL 和密度。
- **权威（Authority）**：不得意外取得运行时、网络、持久化或特权能力的所有权。

每项有意偏离上游的差异都必须归入以下一种：`primitive-adaptation`、`theme-adaptation`、`authority-boundary`、`accessibility-fix`、`bug-fix` 或 `unsupported-upstream-behavior`。未分类的差异属于未完成工作。

## 7. 验证门禁

先运行最窄的相关检查，再执行包级检查：

- 对修改的包运行类型检查和 lint。
- 测试受控/非受控状态、回调、复合组合，以及所有有意义的空、加载和错误状态。
- 对交互原语测试键盘导航、焦点恢复、可访问名称及 Escape/外部点击行为。
- 运行真实浏览器 smoke，覆盖窄屏、浅色/深色、RTL 和组件的主要交互路径。
- 扫描已完成移植的文件，查找残留的上游运行时导入和被禁止的权威能力导入。文本合并干净不等于适配正确。
- 宣称移植完成前，运行包文档要求的构建和测试命令。

大型或高风险移植应补充上游 fixture 或快照，记录固定基线与聚焦行为矩阵。不能仅凭源码逐字节相等判断还原质量：Aboard 会有意修改原语和主题 Token。

## 8. 迁移记录

`SOURCES.md` 继续作为包级来源索引。复杂组件或有实质行为差异时，补充聚焦迁移记录，包含：

- 上游源码与固定版本；
- 修改的文件与适配分类；
- 明确保留不动的文件；
- 行为差异及原因；
- 聚焦检查与人工浏览器 QA；
- 已知缺口和后续工作。

迁移记录必须基于事实，不能混淆 `implemented`、`partial`、`designed`、`deferred` 和 `unsupported`。

## 9. 升级流程

升级上游源码时，复制前先对比新旧固定基线。重新执行原语核对、适配审阅、残留导入扫描、聚焦测试、浏览器矩阵和许可证审阅。禁止在未保留、审阅 Aboard 修改的情况下，整份覆盖已定制的移植实现。
